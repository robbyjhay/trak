# Phase 04 — Production Hardening & CI/CD

## Context
With the PostgreSQL database and WebSocket server in place, the application was technically functional as a full-stack system, but it still lacked the security boundaries and operational resilience required for deployment.

## Starting Point
The application still possessed lingering insecure practices from the prototyping phase, such as shared default passwords, hardcoded JWT secrets, and a lack of automated testing or environment checks.

## Trigger
Continuing the execution of the Audit Remediation Plan (specifically Phase 4: Production Hardening), it was necessary to secure the application boundaries before any real user data could be introduced.

## Work Performed
1. **Authentication Overhaul**: I implemented secure session-based authentication using `jose` for JWTs and `bcrypt` for password hashing. The "mock roster" login was completely replaced by a secure credential flow.
2. **Endpoint Security**: The public RSVP endpoint was secured using a cryptographic `rsvpTokenHash` generated by the database, closing a major injection vulnerability.
3. **Storage Integration**: File attachments were migrated from temporary client-side blobs to AWS S3 via presigned URLs.
4. **CI/CD & Testing**: I configured Vitest for unit testing and Playwright for End-to-End (E2E) testing. A GitHub Actions CI pipeline was established (evidenced by commits fixing Prisma generation in CI).
5. **Environment Configuration**: I enforced strict `.env` loading and created scripts (`check-prod-env.mjs`) to ensure the application fails to boot if critical secrets are missing.

## Product Changes
Users now experienced a standard, secure login flow. They were forced to change their default passwords upon first login. RSVP links became secure, single-use tokens.
